# Industrial & Research Precise Code Indexers

Research slice 03 for **codectx** (Go CLI + MCP server; SQLite index; tree-sitter base layer, optional SCIP import, optional LSP overlay, optional Joern CPG).

**Method.** Every non-obvious claim carries a URL. Where no primary figure exists, the cell says **no published figure found** rather than an estimate. *[Speculation]* marks inference, not a source.

---

## 1. Sourcegraph SCIP (+ scip-typescript / scip-java / scip-go / scip-clang)

- **(a) Compiler required, per language.** SCIP is a format; each indexer wraps a real frontend. `scip-typescript` is built on the TypeScript type checker and "indexing performance is largely bottlenecked by type checking performance" ([blog](https://sourcegraph.com/blog/announcing-scip-typescript)); `scip-java` runs a `semanticdb-javac` compiler plugin. Producers also include scip-clang/ruby/python/dotnet/dart and rust-analyzer's `scip` subcommand.
- **Model.** `Index → Metadata + [Document] + [external SymbolInformation]`; an `Occurrence` binds a range to a **symbol string** plus a `symbol_roles` bitset (`Definition 0x1, Import 0x2, WriteAccess 0x4, ReadAccess 0x8, Generated 0x10, Test 0x20`). The load-bearing decision is the symbol grammar ([scip.proto](https://raw.githubusercontent.com/sourcegraph/scip/main/scip.proto)): `<symbol> ::= <scheme> ' ' <package> ' ' (<descriptor>)+ | 'local ' <local-id>`, descriptors suffixed `/` namespace, `#` type, `.` term, `()` method, `!` macro. Readable global IDs replace LSIF's `moniker`/`resultSet` indirection.
- **(b) File-level incrementality is a property of the format, not the extractors.** Goals include "cross-repository navigation, **file-level incrementality**, and parallelization" ([DESIGN.md](https://raw.githubusercontent.com/sourcegraph/scip/main/docs/DESIGN.md)); string symbols make each `Document` independently replaceable. Producers stay whole-project: tsc/javac typecheck the world.
- **(c) Storage / size.** Protobuf, for a "relatively compact binary format", "easy code generation", "streaming reads and writes". Uncompressed compactness is an explicit **non-goal**: "SCIP data tends to have a compression ratio around in the range of 10%-20%". Ranges are packed varint arrays, roughly halving payload ([DeepWiki](https://deepwiki.com/sourcegraph/scip)). Versus LSIF: "LSIF indexes are on average **4x larger when gzip compressed**… Uncompressed LSIF payloads are **~5x larger**" ([announcement](https://sourcegraph.com/blog/announcing-scip)). **No index-size-vs-source ratio published**; GitLab's 200 MB artifact cap is the nearest proxy ([GitLab](https://docs.gitlab.com/user/project/code_intelligence/)).
- **(d) Throughput.** `scip-typescript`: "**1k-5k lines per second** depending on the usage of types", "3-10x speedups" over `lsif-node`; Sourcegraph's CI job "went from ~40 minutes (12 parallel jobs) down to ~5 minutes (1 job)". Scale: "over 45k repositories… more than 4k LSIF uploads per day". *Caveat:* widely-cited scip-java figures (SemanticDB slowing compilation 45–50%) trace to a benchmarks page that now **404s**, with `docs/benchmarks.md` gone from the repo (verified via the GitHub contents API). Unverifiable.
- **(e) Traded.** Nothing semantically. The trade is **operational**: a build per project per language, freshness lagging a CI cycle. SCIP is also deliberately not queryable — "standalone efficient navigation" is a non-goal.

## 2. LSIF — the predecessor, and why it lost

- **(a)–(c)** Dump an LSP server's knowledge so queries work without running it ([spec](https://microsoft.github.io/language-server-protocol/specifications/lsif/0.6.0/specification/)): a JSON-lines property graph of vertices (`document`, `range`, `resultSet`, `definitionResult`, `moniker`) and edges (`contains`, `next`, `item`) wired by integer `id`s. 4–5× larger than SCIP — "LSIF indexes are on average 4x larger when gzip compressed… Uncompressed LSIF payloads are ~5x larger" ([announcement](https://sourcegraph.com/blog/announcing-scip)); GitLab still uses it, capped at 200 MB, "one LSIF file per project" ([GitLab](https://docs.gitlab.com/user/project/code_intelligence/)).
- **(b) Incrementality: effectively repo-level.** "The heavy usage of opaque global IDs imposes an ordering constraint on how symbols… get added… Globally incrementing IDs make it difficult, as well, to update an existing index with new information for only a subset of the documents" ([announcement](https://sourcegraph.com/blog/announcing-scip)).
- **(e) Why replaced.** No machine-readable schema → slow indexer development; "Slow performance caused the need to hold large in-memory data structures when writing or reading the graph encoding"; opaque numeric IDs make payloads undebuggable. The sharpest point: with integer IDs, "off-by-one bugs in indexers cause code navigation to fail **repo-wide**" ([DESIGN.md](https://raw.githubusercontent.com/sourcegraph/scip/main/docs/DESIGN.md)).

## 3. Google Kythe

- **(a) Compilation required, hermetically.** An extractor hooks the build and captures each compilation "with enough information to enable **replaying the compilation to the front-end of the compiler**" — a `CompilationUnit` protobuf plus every input, in a `.kzip` ([kzip](https://kythe.io/docs/kythe-kzip.html)). Java extraction "works by intercepting all calls to javac"; C++ uses `cxx_extractor`. **(b)** Unit = **compilation unit / kzip**; a changed header re-triggers every including TU.
- **Model.** Flat entries: `(source VName, edge kind, target VName, fact name, value)`, VName = `(signature, corpus, root, path, language)`; nodes `anchor` (byte offsets), `file`, `record`, `function`; edges `defines/binding`, `ref`, `childof`, `typed` ([schema](https://kythe.io/docs/schema/)).
- **(c) Storage vs serving is explicitly split.** The GraphStore "is to be further processed into more efficient formats for searching or serving, e.g. into **denormalized paged association tables**" ([storage](https://kythe.io/docs/kythe-storage.html)) — the xrefs table is one pre-joined row per symbol.
- **(d)–(e)** **No published throughput or index-size figure found** for Kythe itself. Little precision is traded; what you lose is anything you cannot build, plus keystroke latency — the storage→serving pipeline is a batch job.

## 4. Meta Glean

- **(a)** Glean is the *database*; indexers are pluggable, mostly compiler-derived, and it ingests SCIP directly ([Meta](https://engineering.fb.com/2024/12/19/developer-tools/glean-open-source-code-indexing/)). Datalog-flavoured: facts are rows with a prefix-indexed key and a value; predicates are **stored** or **derived**; queries in Angle.
- **(b) "Stacked databases" — the most sophisticated incrementality here.** "To produce a modified DB, we hide a portion of the data in the original DB, and then stack a DB with the new data on top" ([blog](https://glean.software/blog/incremental/)). The unit is an **ownership unit**, usually a filename; ownership sets are unions/intersections with their own ids, and visibility is a bitmap over them ([docs](https://glean.software/docs/implementation/incrementality/)). The hard invariant — "every fact referenced by a visible fact is also visible" — is enforced by propagating owner `A || B` from referrer to referee in reverse fact order, O(facts) time and space. Derived facts get a **conjunction** of their sources' owners, disappearing exactly when any input does.
- **(c)–(d)** RocksDB; ownership sets use **Elias-Fano coding** and fact→ownership is an **interval map**, so "keeping all this information only adds about **7%** to the DB size". Independent Haskell benchmark over 2,922 Stackage packages: **Glean 0.8 GB / 470 s vs hiedb 5.2 GB / 1,021 s** ([vs hiedb](https://simonmar.github.io/posts/2025-05-22-Glean-Haskell.html)); find-references on `Data.Aeson.encode` took hiedb 2.3 s against raw Glean **0.03 s**. Incrementality overhead: "2-3% for Python, for Hack it was in the noise" at index time; "less than 10% for 'typical' queries", but "Queries that do a lot of searching may be impacted by around **3x**".
- **(e) Traded.** None inherent. The costs are operational complexity (docs flag an unimplemented case where derived facts in stacked DBs "may become inconsistent") and that 3× search tax.

## 5. GitHub stack-graphs / tree-sitter-graph

- **(a) Name resolution *without* a compiler.** "Stack graphs can be constructed via a **purely syntactic analysis** of the program's source code… we can extract name binding information for every repository without any per-package configuration, and without having to invoke an arbitrary, untrusted, package-specific build process" ([Creager & van Antwerpen](https://arxiv.org/abs/2211.01224)). Mechanism: tree-sitter CST → `tree-sitter-graph` stanzas → a graph where reference nodes *push* symbols and definition nodes *pop* them; a valid binding is a path whose symbol-stack operations balance, with edge *precedence* encoding shadowing ([blog](https://github.blog/open-source/introducing-stack-graphs/)). A second **scope stack** handles type-directed lookup.
- **(b) Per file, by construction.** "for each source file, we create an **isolated subgraph** without any knowledge of, or visibility into, any other file in the program. This lets us eliminate the storage and compute costs of reanalyzing file versions that we have already seen." Cross-file resolution defers to **partial paths**, concatenated at query time "by unifying the left-hand side's postcondition with the right-hand side's precondition" ([ar5iv](https://ar5iv.labs.arxiv.org/html/2211.01224)).
- **(c)–(d)** "each file's subgraph can be identified and stored independently" — the natural key is (file content, language), not (repo, commit); **no published size figure found**, and **no quantitative evaluation exists in the paper**, verified against arXiv and the OASIcs version ([DROPS](https://drops.dagstuhl.de/entities/document/10.4230/OASIcs.EVCS.2023.8)). The blog claims "sub-100ms navigation" but publishes no index timings.
- **(e) Traded.** Acknowledged gaps: dataflow (tracing parameter values to resolve a call) and generic-type inheritance. Coverage is the real constraint — precise nav shipped for **Python** first ([announcement](https://github.blog/news-insights/product-news/precise-code-navigation-python-code-navigation-pull-requests/)). *[Speculation: per-language DSL authoring cost, not runtime cost, is why it never swept all languages.]*

## 6. GitHub tree-sitter *tags* (search-based navigation) — the pragmatic 90%

The system that actually ships to every language, and the closest published analogue to codectx's base layer.

- **(a)** tree-sitter parse → a `tags.scm` tree-query → filter-map over the CST yielding `@definition.function`, `@reference.call`, etc., each with an inner `@name` capture ([docs](https://tree-sitter.github.io/tree-sitter/4-code-navigation.html)). No compiler, no config, no build. Resolution is **name matching**: it "searches all definitions and references across a repository to find entities with a given name" ([GitHub](https://docs.github.com/en/repositories/working-with-files/using-files/navigating-code-on-github)). Minimal scope state where syntax demands it — for Ruby, "you must record the names of any local variables in a given Ruby scope" ([CACM](https://cacm.acm.org/practice/static-analysis-at-github/)).
- **(b) Per git blob, content-addressed.** "since this is the **SHA1 hash of the blob contents**, once a blob is parsed, it never needs to be parsed again and can be shared across any commit that includes that blob." Incrementality is free *and global* — across commits, branches, repositories.
- **(c)** MySQL → Vitess-sharded MySQL → **immutable files in Azure Blob Storage**: symbol-names-by-2-char-SHA1-prefix (TSV); index-blobs-for-a-commit (a header of section byte offsets, then TSV sections sorted by path and by blob SHA, enabling **binary search in both directions**); per-blob defs+refs files where "Definitions are stored first, so that find operations can return early once the first reference is reached". **No size ratio published.**
- **(d) The best published numbers in this survey.** "more than **1,000 pushes per minute**… more than **two million new identifier names per minute**. The p99… for the first-time index of a repository is **~60 seconds** (the 50th percentile is ~1.1 seconds). The p99 for an **incremental index is ~10 seconds** (p50 is ~1.3 seconds). The system serves 30,000 requests per minute for symbol lookup, with p99 request times on the order of **90 milliseconds**." Nine languages, six million repositories.
- **(e) Traded.** Everything a compiler knows — overloads, shadowing, imports, generics, dynamic dispatch collapse to "same name". Their framing: full analysis "must, in essence, run a build of the software… results are generally available in **minutes, not the seconds** that code navigation relies upon", so they chose "**basic analysis techniques**… with **zero configuration**".

## 7. rust-analyzer / salsa

- **(a)** A from-scratch compiler frontend (parser, name resolution, type inference); never invokes `rustc`. Metadata from `cargo metadata`.
- **(b)** The unit is a **query** — "a bundle of function with arguments" ([Durable Incrementality](https://rust-analyzer.github.io/blog/2023/07/24/durable-incrementality.html)). Salsa memoizes queries, records dependency edges seen during execution, bumps a global revision counter on input change, and *backdates* results whose dependencies did not change. **Durability** is the scaling fix: inputs are tagged `volatile`/`normal`/`durable` (your code / crates.io / std) in a **version vector**, so bumping `volatile` never invalidates the `durable` subgraph. Without it, "any change to `src/lib.rs` necessitates checking all the queries related to standard library (which adds up to about **300ms**)".
- **(c)–(e)** In-memory only; nothing persists across restarts, and **no published LOC/s figure found** — the target is keystroke latency. The notable data point is negative: after the salsa 3.0 port, memory on a large codebase went "from 5-6GB before the update to 22GB shortly after starting and up to 30GB during use" ([#19402](https://github.com/rust-lang/rust-analyzer/issues/19402)). Macros and `build.rs` codegen are approximated.

## 8. gopls

- **(a)–(b)** `go/packages` + `go/types` — a real typechecker, no compiler binary. "In Go, the units are **packages**" ([Scaling gopls](https://go.dev/blog/gopls-scalability)); the core tension is that "the basic unit of operation for the type checking is the package, but the basic unit of operation for an editor is the file" ([design.md](https://raw.githubusercontent.com/golang/tools/master/gopls/doc/design/design.md)). v0.12 added **fine-grained invalidation** via "a simplified graph of symbol references in memory", so a change not altering a package's exported API stops cascading.
- **(c)** Hybrid: a persistent, transactional file-based key/value store (`filecache`) holding serialized `xrefs`, `methodsets` and `typerefs` indexes, with in-memory caches above; snapshots are immutable views ([implementation.md](https://go.googlesource.com/tools/+/refs/heads/master/gopls/doc/design/implementation.md)).
- **(d)–(e)** Memory "savings average around **75%**" post-v0.12 across "28 of the most popular Go repositories on GitHub", non-linearly better on larger projects. The motivating ratio: "**typed syntax trees are typically 30x larger than the source text**". **No on-disk index size published.** No semantic loss; trades cold-start latency and a package-granular blast radius.

## 9. clangd background index

The most directly transferable shard design for codectx: per-TU shards plus a merge layer.

- **(a)** `SymbolCollector` runs over a real Clang AST — "extracts indexable data from a **translation unit**"; requires `compile_commands.json`. Three objects: **Symbols** ("Two declarations of the same thing will produce the same `SymbolID` and thus be merged into one `Symbol`"), **Refs**, **Relations** ([index docs](https://clangd.llvm.org/design/indexing)).
- **(b)–(c)** Unit = **translation unit**, one `.idx` shard per file: "Before indexing each file, the index checks for a cached `*.idx` file on disk… This avoids reindexing on startup if nothing changed since last time." A dynamic `FileIndex` over open files sits above the background `Dex` — "a more complex one with a scalable `fuzzyFind` search" (inverted index over symbol-name trigrams plus scope/proximity signals), versus `MemIndex` which is "cheap to construct" ([walkthrough](https://clangd.llvm.org/design/code)).
- **(d)** Chromium (incl. v8, blink): "~**550 MB** disk space", "~**2.7 GB** memory in clangd", and "the first index time may take hours (for reference, it took **2~3 hours on a 48-core, 64GB machine**)" ([Chromium docs](https://chromium.googlesource.com/chromium/src.git/+/HEAD/docs/clangd.md)). At ~10^7 LOC that is order **10^3 LOC/s/core**.
- **(e)** Header-heavy C++ means massive redundancy: each header is re-parsed once per including TU — that is where the hours go.

## 10. universal-ctags / GNU GLOBAL / cscope — why they are instant

The only tier with *published index-size-to-source ratios*, making it the best calibration point for codectx.

- **(a)–(b)** All lexer/regex-based, no compilation. ctags: "Because ctags is neither a preprocessor nor a compiler, use of preprocessor macros can fool ctags"; "it has garbage in, garbage out (GIGO) feature" ([ctags(1)](https://docs.ctags.io/en/latest/man/ctags.1.html)). cscope uses a "fuzzy parser" for C and "rebuilds the cross-reference only if a source file has changed" ([cscope](https://cscope.sourceforge.net/)). GNU GLOBAL adds plug-in parsers ("You can use Universal Ctags as a plug-in parser too") and per-file incremental update via `-u` and `--single-update` ([manual](https://www.gnu.org/software/global/manual/global.html)).
- **(c) Sizes — the key numbers.** GNU GLOBAL on Linux-2.6.32 ([manual](https://www.gnu.org/software/global/manual/global.html)): "source code(Linux-2.6.32) **390MB** / GPATH **6MB** / GTAGS **81MB** / GRTAGS **202MB** / total of tag files **289MB**" — **0.74× source**, with the *reference* DB 2.5× the *definition* DB. cscope on a Linux 2.4.18 subset: "**25 megabytes**" against "150 MB of source code" (~0.17×) ([cscope](http://cscope.sourceforge.net/large_projects.html)). ctags is sorted plain text — "The tags file is sorted on {tagname}. This allows for a binary search in the file" ([FORMAT](https://ctags.sourceforge.net/FORMAT)); GLOBAL's files are **"SQLITE3 databases. Each database has a table named 'db'"** under `--sqlite3` ([help-global](https://lists.gnu.org/archive/html/help-global/2018-12/msg00002.html)).
- **(d) Throughput.** Maintainers' benchmark over linux + php-src + ruby, C parser: "**27886 files, 19784832 lines (555082 kB) scanned in 15.1 seconds (36686 kB/s)**" ([codebase](https://github.com/universal-ctags/codebase)) — roughly **1.3 M LOC/s single-process**. Full kernel, all languages: single-threaded **1m13s–1m26s**, 8 parallel workers **~29 s** ([ctags#1874](https://github.com/universal-ctags/ctags/issues/1874)).
- **(e) Traded.** "Duplicate tags are allowed, but which one is actually used is unpredictable (because of the binary search)"; C++ scope is guessed — "ctags cannot determine whether the scope specifier is a class name or a namespace specifier"; reference tagging is "new and limited to specific areas of specific languages".
- **Worth stealing:** ctags emits JSON Lines (`--output-format=json`) and offers a REPL — `--_interactive` "enters a REPL… json commands are received over stdin", with a `sandbox` submode ([interactive mode](https://docs.ctags.io/en/latest/interactive-mode.html)).

## 11. Zoekt / Livegrep / Google Code Search — the text tier

- **(a)–(b)** No parsing. Zoekt "build[s] an index of ngrams (n=3), where we store the offset of each ngram's occurrence within a file" — **positional** trigrams — sharded per repo and atomically swapped on rebuild ([design.md](https://raw.githubusercontent.com/sourcegraph/zoekt/main/doc/design.md)). Livegrep instead builds a **suffix array**, which is why it cannot update incrementally: suffix arrays "are elegant but difficult to scale and update dynamically since they require concatenating all content into a single string" ([Elhage](https://blog.nelhage.com/2015/02/regular-expression-search-with-suffix-arrays/)).
- **(c)** Zoekt: "it is about **3x the corpus size**, composed of 2x (offsets), and 1x (original content)"; "In practice, the shard size is about **3.5x the corpus size**"; "searching with positional trigrams only requires **1.2x corpus size** of RAM since the posting lists can be stored on SSD".
- **(d)–(e)** Zoekt targets "sub-50ms results on large codebases, such as Android (~2G text) or Chrome". Google Code Search: 1.5 TB indexed, ~200 QPS, **median commit→searchable <10 s**; its "sparse n-gram solution" is "more than **500 times more efficient** than the brute-force solution", and indexing *full history* costs "a factor of just **2.5**" ([SWE at Google ch. 17](https://abseil.io/resources/swe-book/html/ch17.html)). Zero semantics: everything is a substring.

## 12. Semgrep

- **(a)** tree-sitter parsers via [ocaml-tree-sitter-semgrep](https://github.com/semgrep/ocaml-tree-sitter-semgrep) plus a generic AST; **no build required**. The OSS boundary is stated plainly: "By design… Semgrep Community Edition (CE), can only analyze interactions within a single function, also known as **intraprocedural analysis**. This limited scope makes Semgrep CE fast and easy to integrate into developer workflows" ([Pro intro](https://docs.semgrep.dev/semgrep-code/semgrep-pro-engine-intro)). "Interprocedural taint analysis is a Semgrep Pro feature".
- **(b)–(c)** Per **file** in CE, with **no persistent index** (the changelog records "Removed the AST caching experimental feature"). Pro adds cross-function and cross-file, but "Cross-file analysis is not supported for diff-aware scans" — deep mode and incremental mode are mutually exclusive ([CI docs](https://docs.semgrep.dev/deployment/customize-ci-jobs)). Cross-file pre-processing self-limits: above "**5 GB** of memory… the scan uses single-file analysis".
- **(d)** Average CI scan time for OSS scans is "**just under 10 seconds**"; full OSS scans "around **20 seconds**"; full Pro scans "**under 300 seconds**" ([speed blog](https://semgrep.dev/blog/2023/semgrep-speed/)). At the tail, P95 was "10 minutes" and P99 "~45 minutes"; interfile scans time out at 3 hours and fall back to single-file.
- **(e)** Documented and blunt: "No path sensitivity", "No pointer or shape analysis", "No soundness guarantees", "**Expect both false positives and false negatives**" ([dataflow overview](https://docs.semgrep.dev/writing-rules/data-flow/data-flow-overview)).

## 13. CodeQL

- **(a) The heaviest option here.** "CodeQL analysis relies on **extracting relational data** from your code"; for compiled languages "CodeQL needs to **invoke the required build system** to generate a database, therefore the build method must be available to the CLI" ([docs](https://docs.github.com/en/code-security/codeql-cli/getting-started-with-the-codeql-cli/preparing-your-code-for-codeql-analysis)). JS/TS, Python, Ruby need no build. **(b) Incrementality: none** — a whole-snapshot artifact rebuilt per analysis.
- **(c)–(d)** A directory of relational tables *plus a full source archive*; a reported Chromium database was **762 MB** ([codeql#8755](https://github.com/github/codeql/issues/8755)). Recommended hardware: <100 K LOC → 8 GB / 2 cores; 100 K–1 M → 16 GB / 4–8 cores; **>1 M LOC → 64 GB RAM / 8 cores**, always with "an SSD with **14 GB or more** of disk space" ([hardware](https://docs.github.com/en/code-security/reference/code-scanning/codeql/recommended-hardware-resources-for-running-codeql)). No vendor LOC/s figure. A user report: autobuild on Java/Kotlin "taking 4 hours compared to regular builds of 20-30 minutes" ([codeql-action#2378](https://github.com/github/codeql-action/issues/2378)). Independently, "roughly **43 minutes**" for the Wireshark database on 4 CPUs / 16 GB — where **Joern's CPG for the same project OOM'd at 16 GB and took "something around 6 hours" on a 128 GB machine** ([Joern vs CodeQL](https://elmanto.github.io/posts/sast_derby_joern_vs_codeql)); Joern needs no build but pays in fuzzy-parse imprecision ([docs](https://docs.joern.io/)).
- **(e) Traded.** Almost nothing semantically — it does whole-program dataflow and taint. It trades *everything else*: a hermetic build, tens of GB of RAM, hours of wall clock, zero interactivity. GitHub's own navigation team rejected it for code nav on these grounds (§6).

## 14. Infer

- **(a)** Two phases. **Capture** translates compiler invocations into Infer's IR — with a stark consequence: "if no file gets compiled, also no file will be analyzed" ([workflow](https://fbinfer.com/docs/infer-workflow/)). **Analyze**: "Infer analyzes each function and method separately", via bi-abduction over separation logic, now Pulse.
- **(b)–(c) Procedure-level summaries — the only genuinely incremental interprocedural design here.** "Passing `--reactive` (or `-r`) to Infer prevents it from deleting `infer-out/`, leading to a _differential_ workflow"; CI guidance is "determine the modified files, and run the analysis in reactive mode starting from those files" ([CI steps](https://fbinfer.com/docs/steps-for-ci/)). "All disk artefacts… are now stored in the SQLite database in infer-out/results.db", summaries included ([Changelog](https://github.com/facebook/infer/blob/main/Changelog.md)).
- **(d) The best incrementality speedup figure in this survey.** On OpenSSL, "over 300,000 lines of code and 700 files": `infer capture` **5m00s**; full `infer -j 1 analyze` **22m20s**; incremental `infer -j 1 run -reactive` **41s** ([Meta](https://engineering.fb.com/2017/09/06/android/finding-inter-procedural-bugs-at-scale-with-infer-static-analyzer/)) — a **~33× reduction** from summary reuse.
- **(e)** Deliberate unsoundness: "Pulse makes optimistic assumptions about calls to unknown functions… this may cause false negatives as well as false positives"; errors are reported only "when all conditions on the erroneous path are true regardless of input", else suppressed as *latent*.

## 15. SonarQube

- **(a)** Per-language analyzers over their own parsers. **Java requires bytecode**: "Compiled `.class` files are required for Java projects with more than one Java file", else analysis fails outright ([Java docs](https://docs.sonarsource.com/sonarqube-server/10.8/analyzing-source-code/languages/java)); C/C++/Obj-C need a Build Wrapper. Cross-procedural reach is file-scoped: "all non-overridable methods defined in the same file as the method under analysis… will be explored and learned from".
- **(b)–(e)** PR-scoped — "only the changed files are analyzed in a pull request context"; server-side storage is a relational DB of issues and measures, **not** a code index. Published target: "analyze a **1M LOC project in less than 18 minutes**", "95% of these projects analyzed within the targets" — roughly **900 LOC/s** ([targets](https://www.sonarsource.com/blog/sonars-analysis-performance-targets/)). But "Behaviors of overridable methods will be approximated" and SE analysis of a path stops at the first issue. Unusable as a navigation backend.

## Patterns

### The cost spectrum

| Tier | Technique | Compiler? | Incrementality unit | Index ÷ source | Throughput | Answers |
|---|---|---|---|---|---|---|
| **1. Text** | trigram / suffix array | no | shard / repo | **3–3.5×** ([zoekt](https://raw.githubusercontent.com/sourcegraph/zoekt/main/doc/design.md)); full history 2.5× | Google commit→searchable **<10 s** | "where does this string appear" |
| **2. **Tier 2 is ~100–1000× cheaper than tier 4; tier 4 is ~10–100× cheaper than tier 5.** Two anomalies matter. Tier 3 buys most of tier 4's *answer* at close to tier 2's *cost*, paying in per-language engineering rather than per-repo compute. And Infer shows tier 5 can be made incremental (33×) if — and only if — the analysis decomposes into per-procedure summaries.

### Recurring design decisions

1. **String keys beat integer keys.** LSIF's integer IDs caused repo-wide failures from off-by-ones, blocked partial update, and imposed ordering constraints. SCIP's fix was symbol strings; Kythe's structured VNames; Glean's typed fact keys. Every system that succeeded at incrementality uses globally-meaningful, locally-computable keys.
2. **Content addressing is the cheapest incrementality that exists.** GitHub keys parsed tags by **git blob SHA**, so a blob parsed once is never parsed again "and can be shared across any commit that includes that blob". clangd shards by file with an `.idx` staleness check. Both dominate timestamp- or commit-based invalidation and are free across branches.
3. **Separate the write format from the serve format, and split defs from refs.** Kythe is explicit that its GraphStore is "storage" while serving needs "denormalized paged association tables"; SCIP disclaims being queryable. Every system keeps definitions and references apart — GTAGS/GRTAGS, Kythe (`defines/binding` vs `ref`), SCIP (`symbol_roles`), GitHub (D/R sections) — and GNU GLOBAL shows why: refs are **202 MB** against 81 MB of defs.
4. **Layering beats one index, and depth rarely survives contact with incrementality.** clangd merges dynamic over background over static; gopls layers memory caches over a file cache; Glean stacks incremental DBs over base DBs — always "smaller and fresher wins". But depth and incrementality are usually exclusive unless you decompose into summaries: Semgrep states "Cross-file analysis is not supported for diff-aware scans", CodeQL has no incremental path, and Infer is the lone exception precisely because of procedure summaries.
5. **The winning products chose the cheap tier.** GitHub ships tier 2 to nine languages at 1,000 pushes/min with zero configuration, tier 3 to a handful; nobody has shipped tier 4 to all languages without a build. Compression is an afterthought that pays: SCIP skips uncompressed compactness because gzip gives 5–10×, and Glean's ownership metadata costs only 7% of DB size.

## Implications for codectx

1. **Key the tree-sitter base layer on blob content hash, not path + mtime.** Store per-file facts under `sha256(bytes) + language + grammar version` — GitHub's highest-leverage decision ("once a blob is parsed, it never needs to be parsed again"). Incrementality then comes free across branches, worktrees and vendored copies. Schema: `blob(hash, lang, grammar_ver)`, `symbol`/`occurrence` keyed on `blob_id`, plus a thin `commit_files(commit, path, blob_id)` join — so re-indexing a commit costs the set-difference of blob hashes.

2. **Split definitions and references into separate tables, defs ordered first.** Independently arrived at by GTAGS/GRTAGS, Kythe, SCIP and GitHub — and GNU GLOBAL quantifies why: references are **2.5× the size of definitions** (202 MB vs 81 MB on the kernel). Go-to-definition must be a hot, index-covered lookup; find-references is a cold range scan. Do not merge them behind a `kind` column.

3. **Budget the structural layer at 0.2–0.75× source, not "negligible".** GNU GLOBAL's kernel index is 289 MB against 390 MB of source (**0.74×**); cscope's is ~0.17×. These are the only published ratios in this space. Above ~1× source you are storing too much — likely full text, or un-interned identifier strings. Intern symbol names into their own table.

4. **Adopt SCIP's symbol *string* as the universal join key across all four layers.** This is what lets tree-sitter facts, imported SCIP, LSP results and Joern nodes coexist in one schema without a mapping table. Tree-sitter fills only the descriptor tail (`Foo#bar().`), leaving `scheme`/`package` synthetic; SCIP import fills them properly; the two unify on the descriptor suffix. Avoid LSIF-style integer IDs — they make "off-by-one bugs… fail repo-wide", which for a local tool means silent, whole-repo-wrong answers.

5. **Set per-tier throughput budgets and treat violations as architecture bugs.** Anchors: tier 2 at ~10^6 LOC/s single-process, tier 4 at ~10^3 LOC/s/core. A 1 M-LOC repo should be structurally indexed in **single-digit seconds**; if it takes minutes, suspect failure to parallelise per file, or one SQLite transaction per file. ctags gets only ~2.8× from 8 workers, so expect parallel gains to be sublinear and I/O-bound.

6. **Make precise layers strictly optional overlays with independent freshness, and encode that in the data.** clangd's merge order (open > background > static) and Glean's stacked DBs both encode "smaller and fresher wins". Give every fact a `provenance` (treesitter / scip / lsp / joern) and a `computed_at_blob`, so a query can answer "is this binding compiler-verified or name-matched?" Never silently blend them: an agent consuming MCP results needs to know whether `find_references` is exact or heuristic.

7. **Do not build an incremental SCIP importer; build an idempotent per-document replacer.** SCIP's file-level incrementality is a property of the format, not the indexers — tsc/javac/clang still typecheck the world. Realistic pipeline: the user runs a full indexer on demand or in CI, codectx ingests the `.scip`, and ingestion *replaces* rows per `Document` path rather than truncating. Use protobuf streaming so a large index never lands fully in memory.

8. **Keep tier 5 off the interactive path; for interprocedural facts copy Infer's shape, not CodeQL's.** Wireshark's CPG took ~6 h on 128 GB and OOM'd at 16 GB, so Joern belongs in explicit, user-initiated background queries with a cached result set — never behind `go_to_definition`. Infer shows the alternative: per-procedure summaries in a SQLite `results.db`, composed bottom-up over the call graph, turning a 22-minute full run into a 41-second reactive one. A `call_graph` table plus per-symbol summary rows fits codectx's storage model far better than a whole-program graph. *[Speculation: even trivial summaries — "returns its argument", "writes to disk" — would help an agent and are cheap to derive from tree-sitter plus the call graph. Likewise, stack-graphs is the only published route to real name binding with file-granular incrementality and no build, but its paper has no quantitative evaluation and per-language rule sets are large; a narrow scope-resolution pass over tree-sitter CSTs — imports, locals, member access within a file — probably captures most of the benefit and degrades to name matching rather than failing.]*
