# 17 — Where the library conflicts with codectx's product rules, and the mechanism for each

Companion to `../features/09-product-rule-conflicts.md` (written separately); this file keeps the findings of the feature-matrix pass that that file does not carry (the DisjunctionMax defect, the silent caps, block-max inexactness, the payload and add_segment routes). Version: tantivy 0.26.2. Paths are inside `tantivy-0.26.2/`. codectx references are at commit 16dfef6. The rules come from the benchmark brief: complete answers with no top-k cap, deterministic ranking, statistics over visible documents only, and retained snapshots with soft-deleted documents.

## 1. Complete answers, no top-k cap
- Conflict: the library's ranked collector is `TopDocs`, which requires a limit (`with_limit(0)` panics, `src/collector/top_score_collector.rs:93-96`) and is built to prune. Its block-max upper bounds "may lead us to return a lesser document" when there is more than one segment (`src/query/term_query/term_scorer.rs:58-70`). Several other APIs cap silently: `PhrasePrefixQuery` expands at most 50 terms by default (`src/query/phrase_prefix_query/phrase_prefix_query.rs:8`), a terms aggregation returns 10 buckets by default (`src/aggregation/bucket/term_agg.rs:316`), `InvertedIndexRangeQuery::limit` (`src/query/range_query/range_query.rs:144`), the `default` tokenizer drops tokens of 40 bytes or more (`src/tokenizer/tokenizer_manager.rs:60-63`), and the indexer drops tokens over 65 530 bytes (`src/postings/postings_writer.rs:141-147`).
- A further correctness trap: `DisjunctionMaxQuery` over frequency-reading term queries, collected by score-ordered `TopDocs`, sums the disjuncts instead of taking the max (verified; see `12-queries.md`).
- Mechanism: a custom `Collector` that keeps every live `(doc, score)` and sorts after `merge_fruits` (the `Collector` trait, `src/collector/mod.rs:156-235`), or `DocSetCollector` (`src/collector/docset_collector.rs:12`) followed by scoring. Both turn off every pruning feature, so for codectx's product mode block-WAND, lazy scorers and TopN thresholds are irrelevant: they cannot be used without breaking the rule. Avoid `PhrasePrefixQuery`, the `default` analyzer and capped aggregations; set explicit limits where they exist.

## 2. Deterministic ranking
- Conflict: `Score` is `f32` (`src/lib.rs:314`); codectx scores in f64 and quantizes to 1e-6 before comparing (codectx `internal/search/bm25.go`, `quantizeScore`). Ties in `TopNComputer` break on ascending `DocAddress` (`top_score_collector.rs:503-510`), and doc addresses depend on thread count, flush points and merges, so two builds of the same corpus can order equal scores differently.
- Mechanism: (a) tuple sort keys, e.g. `order_by(((SortBySimilarityScore, Order::Desc), (SortByString::for_field("id"), Order::Asc)))`, verified to break ties on `id` (see `14-collectors-and-aggregations.md`); still f32. (b) Product mode's own f64 scoring and codectx's comparator over the complete set, which is what the bench's Rust arm does. (c) Build with 1 indexing thread and `NoMergePolicy` + one final merge, so doc ids follow add order.

## 3. Statistics over visible documents only
- Conflict: N is `max_doc` (`src/query/bm25.rs:40-44`), df comes from `TermInfo.doc_freq` (`src/core/searcher.rs:133-141`), and the token total includes deleted documents (`src/index/inverted_index_reader.rs:249-253`). All three include deleted documents until a merge. Verified: after a delete, `doc_freq` stays 2 and explain's N stays 23 while `num_docs` drops to 22 (see `13-scoring.md`). By default the merge policy never merges for deletes (`del_docs_ratio_before_merge = 1.0`, `src/indexer/log_merge_policy.rs:12-15`).
- Mechanism: a `Bm25StatisticsProvider` with alive counts, passed to `search_with_statistics_provider` (`src/core/searcher.rs:193-208`); alive df via the public but scanning `SegmentPostings::doc_freq_given_deletes` (`src/postings/segment_postings.rs:32-36`). It cannot express BM25F (`Bm25Weight::for_terms` is one field, `bm25.rs:100-106`). A lower `set_del_docs_ratio_before_merge` (e.g. 0.1) shrinks but never removes the error. Only product-mode scoring is exact.

## 4. Retained snapshots
- Conflict: `meta.json` holds one commit, and every commit and merge garbage-collects the files the current commit no longer uses (`src/indexer/segment_updater.rs:431-455, 672`; `src/directory/managed_directory.rs:109-152`), including superseded `.del` files (`src/index/index_meta.rs:101-121`). There is no API to open an earlier commit.
- Mechanisms, from strongest to weakest:
  - Within one process, a held `Searcher` is an immutable snapshot that survives later commits and GC (ARCHITECTURE.md, "Searcher"; on Unix mapped files outlive their deletion).
  - One index directory per retained generation. Segments are immutable, so unchanged segment files could be shared by hard link, but tantivy offers no supported way to assemble an index from another index's segments (`IndexWriter::add_segment` is `#[doc(hidden)]`, `src/indexer/index_writer.rs:379-386`).
  - A custom `Directory` whose `delete` is a no-op (trait at `src/directory/directory.rs:133`), plus a saved copy of each commit's `meta.json` (tagged with `PreparedCommit::set_payload`, `src/indexer/prepared_commit.rs:27`) to reopen older segment sets. This works against the library's design and is unsupported.

## 5. Soft-deleted documents
- Fit: deletes are tombstones, i.e. an alive bitset per segment and commit; the postings keep the deleted documents until a merge (ARCHITECTURE.md, "Deletes"). Readers skip them (`src/collector/mod.rs:179-200`). That is soft deletion, but its visibility is "as of the latest commit", not "as of a chosen generation".
- Mechanism for per-generation visibility: `SegmentReader::open_with_custom_alive_set(segment, Some(AliveBitSet))` is public and intersects the custom set with the segment's own deletes (`src/index/segment_reader.rs:147-185`). A product could hold one alive set per generation and run `Weight`/`Collector` per segment itself (`Collector::collect_segment` is a public trait method), because building a `Searcher` from custom readers is `pub(crate)` (`src/core/searcher.rs:267-269`).

## 6. Never freeze the host
- Relevant knobs: indexing threads and per-thread budget, merge threads (`IndexWriterOptions::num_merge_threads`, default 4, `src/indexer/index_writer.rs:60-62`), the search executor (`15-search-runtime.md`), aggregation memory and bucket limits (`14-collectors-and-aggregations.md`), and docstore compression on a dedicated thread (`10-settings-and-fields.md`). A bench run should cap each one and record peak RSS and CPU.

## Summary for the adoption decision
Product mode (custom collector, own f64 BM25F, alive statistics from the alive bitset and `token_count`) satisfies rules 1-3 and 5 today. Rule 4 across processes has no library mechanism; one directory per generation is the honest answer. Library mode (TopDocs + library BM25) violates rules 1, 2 and 3 by design.
