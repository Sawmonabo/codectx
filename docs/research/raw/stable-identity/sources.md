# Raw evidence: stable identity and incremental linking

Excerpts read on 2026-10-09, quoted as fetched. Each entry gives the source's title, its URL and the passage used.

## Symbol identity

1. *SCIP Code Intelligence Protocol* — `scip.proto`, https://github.com/sourcegraph/scip/blob/main/scip.proto
   - "Symbol is similar to a URI, it identifies a class, method, or a local variable."
   - "The list of descriptors for a symbol should together form a fully qualified name for the symbol. That is, it
     should serve as a unique identifier across the package. Typically, it will include one descriptor for every node
     in the AST (along the ancestry path) between the root of the file and the node corresponding to the symbol."
   - Grammar: `<symbol> ::= <scheme> ' ' <package> ' ' (<descriptor>)+ | 'local ' <local-id>`;
     `<method> ::= <name> '(' (<method-disambiguator>)? ').'`.
   - "Local symbols MUST only be used for entities which are local to a Document, and cannot be accessed from outside
     the Document."
   - Ranges belong to occurrences: "Half-open [start, end) range."
2. *SemanticDB specification*, https://scalameta.org/docs/semanticdb/specification.html
   - Overloads: "If the definition is overloaded, the tag is computed from the order of appearance of overloads in the
     source code"; the second gets `+1`. Java: "non-static overloads first, following the same order as they appear in
     the original source", then static overloads.
   - Locals: `local` followed by a number, "unique within the underlying document".
3. *clangd `SymbolID.h`*, https://llvm.googlesource.com/clang-tools-extra/+/refs/heads/master/clangd/index/SymbolID.h
   - A symbol ID is a truncated SHA-1 of the symbol's USR (Unified Symbol Resolution string), "used as a key in the
     symbol indexes".
4. *USRGeneration.cpp history*, https://src.rcs.uwaterloo.ca/source/history/llvm-project/clang/lib/Index/USRGeneration.cpp
   - 2016: parameter types included in the USRs of C functions marked `overloadable`; 2014: return type encoded,
     because function templates can be overloaded by return type.
5. *Roslyn `DocumentationCommentId.cs`*, https://source.dot.net/Microsoft.CodeAnalysis/DocumentationCommentId.cs.html
   - `AppendParameters` writes `(`, each parameter's type separated by `,`, `@` for a by-reference parameter, `)`;
     generic arity as two backticks and a count; a non-void return after `~`.
6. *Kythe storage model*, https://kythe.io/docs/kythe-storage.html
   - Signature: "An opaque signature generated by the analyzer"; it "should be sufficient to distinguish nodes within
     a corpus of the language."
7. *rust-analyzer architecture*, https://rust-analyzer.github.io/book/contributing/architecture.html
   - "`ItemTree` condenses a single `SyntaxTree` into a “summary” data structure, which is stable over modifications
     to function bodies."
   - "The core invariant we maintain is “typing inside a function’s body never invalidates global derived data”."
   - "if you change the body of `foo`, all facts about `bar` should remain intact."
8. *rust-analyzer PR #19837, "Provide better incrementality when items are changed"*,
   https://github.com/rust-lang/rust-analyzer/pull/19837 — merged June 12, 2025.
   - Before: adding or removing an item invalidated the AST id of everything below it in the same file.
   - "Instead of simple numbering, we hash important bits, like the name of the item."
   - Memory: 2392 MB baseline; 2810 MB first version; about 2433 MB with 16-bit hashes and an LRU.
9. *The Python Language Reference*, §8.7 Function definitions,
   https://docs.python.org/3/reference/compound_stmts.html#function-definitions
   - "A function definition is an executable statement. Its execution binds the function name in the current local
     namespace to a function object."
10. Falleri et al., *Fine-grained and accurate source code differencing*, ASE 2014, DOI 10.1145/2642937.2642982; and
    *A Novel Refactoring and Semantic Aware Abstract Syntax Tree Differencing Tool and a Benchmark for Evaluating the
    Accuracy of Diff Tools*, https://arxiv.org/pdf/2403.05939
    - Top-down phase: identical subtrees are found by a hash of label and value; then a bottom-up phase.

## Incremental recomputation

11. Mokhov, Mitchell, Peyton Jones, *Build Systems à la Carte*,
    https://www.microsoft.com/en-us/research/uploads/prod/2018/03/build-systems-a-la-carte.pdf
    - "Definition 2.1 (Minimality). A build system is minimal if it executes tasks at most once per build and only if
      they transitively depend on inputs that changed since the previous build."
    - Fig. 3: "if a comment is added to main.c, the rebuild is stopped after detecting that main.o is unchanged, since
      this indicates that main.exe and its dependents do not need to be rebuilt."
    - §4.2.2 Verifying traces: "record the values/hashes of dependencies used last time, and if something has changed,
      the key is dirty and must [be rebuilt]".
12. *How Salsa works*, rustc-dev-guide, https://rustc-dev-guide.rust-lang.org/queries/salsa.html
    - Salsa checks each downstream computation until it finds one that is not changed, then stops (early cutoff).
13. *Stub Indexes*, IntelliJ Platform Plugin SDK, https://plugins.jetbrains.com/docs/intellij/stub-indexes.html
    - "Typically, it contains only the nodes needed to resolve the declarations contained in this file from external
      files." "Usually there is no need to have stubs for things like statements or local variables."
    - "all information stored in the stub tree depends only on the contents of the file."
14. *Compilation Avoidance*, Gradle blog, November 28, 2022, https://blog.gradle.org/compilation-avoidance
    - Compatible changes: "Making any change to the body of a method"; "Adding, removing, or changing private methods,
      fields, or inner classes". Gradle will "normalize its inputs and generate a unique hash of the ABI."
15. *gopls/internal/lsp/cache: a new analysis driver*,
    https://go.googlesource.com/tools/+/61e2d3f4fee1a8fb382d357fadc53af7828054c0%5E%21
    - "Dependency analysis is based on hashes of only material inputs to each step": "source files, and the types and
      facts of direct dependencies"; changes "(e.g. the insertion of a debugging print statement into a function
      body)" "will usually not invalidate most of the graph."
16. Jay Conrod, *Export data, the secret of Go's fast builds*, https://jayconrod.com/posts/112/export-data--the-secret-of-go-s-fast-builds
    - A change that does not affect a package's exported types leaves its export data the same.
17. *Introducing stack graphs*, GitHub blog, https://github.blog/open-source/introducing-stack-graphs
    - "we look at each file completely in isolation"; "At query time, however, we’re able to bring together the data
      from all files"; "reusing the results that we’ve already calculated and saved for the files that haven’t changed."
18. *Glean: Incrementality*, https://glean.software/docs/implementation/incrementality/
    - Facts are owned by units (typically a file); an incremental database hides changed units of the base; a fact that
      references another extends its ownership so "every fact referenced by a visible fact is also visible."
19. *CodeQL incremental analysis*, https://docs.github.com/en/code-security/how-tos/find-and-fix-code-vulnerabilities/scan-from-the-command-line/incremental-analysis
    - An overlay database over a cached base processes only the changed files.

## Manifest changes

20. TypeScript at v5.9.2, `src/compiler/types.ts` lines 7752–7755 and `src/compiler/commandLineParser.ts`,
    https://github.com/microsoft/TypeScript/tree/v5.9.2/src/compiler
    - `affectsSourceFile?: true; // true if we should recreate SourceFiles after this option changes`
    - `affectsModuleResolution?: true; // currently same effect as affectsSourceFile`
    - `affectsSemanticDiagnostics?: true; // true if option affects semantic diagnostics`
    - Options marked `affectsModuleResolution` include `baseUrl`, `paths`, `rootDirs`, `moduleResolution`, `module`,
      `typeRoots`, `resolvePackageJsonExports`, `resolvePackageJsonImports` and `resolveJsonModule`; `strict` is not.
21. *x/tools/gopls: diff metadata before invalidating on changes to go.mod*, golang/go issue #36589,
    https://github.com/golang/go/issues/36589
    - January 16, 2020: "Right now, `gopls` invalidates all workspace metadata if there is a change to the user's
      `go.mod` file." August 2022: invalidation only on saves to go.mod and go.work. August 20, 2026: "Obsolete. This
      doesn't happen any more."
